# 工作报告撰写

把散落的素材整理成别人愿意看完的报告。报告的价值不在于写了多少，而在于**读的人 30 秒内知道进展、风险和他要做什么**。

## 输入素材（任意组合）

- 日报、任务清单、待办列表
- 会议纪要、群聊记录
- 代码提交记录 / 工单系统记录（`git log --since`、Jira 导出）
- 上一期报告（用于延续未完成项）

## 工作流

### 第 1 步 归集与归一

把每条素材拆成一条记录：

| 字段 | 说明 |
| --- | --- |
| 时间 | 日期，用于排序和本期归属判断 |
| 项目 | 归属项目，多项目时必填 |
| 事项 | 做了什么，动词开头 |
| 结果 | 产出物或状态变化（完成 / 推进到 X / 已上线） |
| 量化 | 数字：完成量、耗时、比例、影响范围 |
| 阻塞 | 卡在哪、卡在谁那里 |

素材里没有"结果"和"量化"的，先标记，别自己编。

### 第 2 步 归类

固定六类，不增不减：

1. **本周关键进展** —— 有实质推进的事，按项目分组
2. **关键成果 / 里程碑** —— 完成、上线、通过验收的事
3. **数据指标** —— 可量化的状态（完成率、处理量、缺陷数、人天消耗）
4. **问题与风险** —— 已发生的问题 + 可能发生的风险
5. **下周计划** —— 具体到事项，不写"继续推进"
6. **需协调 / 需支持** —— 明确要谁、做什么、什么时候

### 第 3 步 撰写规则

1. **动词开头**：完成、交付、修复、上线、推进、验证、梳理、输出。
2. **先结果后过程**，每条不超过 2 行。
3. **能量化的一定量化**：用数量、百分比、人天、时长，不用"大量""显著"。
4. **风险三件套**：影响 + 建议动作 + 需要的支持方。缺任何一项的风险条目无效。
5. **删除无信息量的表述**："继续跟进""保持沟通""按计划推进""加强协同"。
6. **同一件事只出现一次**，不要在前三节重复。
7. **不夸大**：推进到 60% 就写 60%，不要写成"基本完成"。

## 三种篇幅模板

### 极简版（群内同步，5 行以内）

```
【<项目> 周报 09-07 ~ 09-13】
进展：<1 条最重要的>
完成：<1 条>
风险：<1 条，含影响与所需支持>
下周：<2 条>
需要支持：<谁 + 做什么>
```

### 标准周报（1 页）

```markdown
# 周报 | <姓名> | <日期区间>

## 一、关键进展
- **<项目 A>**：<结果>。（<量化>）
- **<项目 B>**：<结果>。（<量化>）

## 二、关键成果
- <完成/上线/验收事项>（<日期>）

## 三、数据指标
| 指标 | 本期 | 环比 | 说明 |
| --- | --- | --- | --- |
| <指标名> | <值> | <±%> | <口径> |

## 四、问题与风险
| 风险 | 影响 | 建议动作 | 需要谁配合 | 期望时间 |
| --- | --- | --- | --- | --- |

## 五、下周计划
1. <事项> —— 目标产出：<产出物>
2. <事项> —— 目标产出：<产出物>

## 六、需协调事项
- 请 <人/团队> 在 <时间> 前 <动作>，否则会影响 <后果>
```

### 向上汇报版（含决策请求）

在标准周报之上，把顺序倒过来：

1. **一句话结论**（本期状态：正常 / 有风险 / 需决策）
2. **需要您决策的 1–2 件事**（选项 + 建议 + 影响）
3. **关键进展**（只留对目标有影响的部分）
4. **里程碑视图**（相对计划的偏差，用 ± 天数表示）
5. **风险与资源诉求**

## 输出规范

- 默认 Markdown；需要正式留档时转 Word（.docx）。
- 面向海外团队时中英双语，数字口径保持统一。
- 成稿后建议过一遍 `text-deai`，去掉"赋能""闭环""持续发力"这类词。
- 日期、人名、项目编号与素材保持一致，不臆改。

## 自检清单

- [ ] 读的人能 30 秒内说清本期最重要的一件事吗？
- [ ] 每条进展都有结果，而不是过程描述？
- [ ] 至少 3 处量化？
- [ ] 每条风险都带影响 + 动作 + 配合方？
- [ ] 下周计划中每条都有明确产出物？
- [ ] 有没有"继续跟进""按计划推进"这类空话？
- [ ] 同一件事没有重复出现在两节？
- [ ] 未完成的上期事项已延续进来？

## 边界

- **不做**：编造数据或成果、替用户承担承诺、把未完成事项写成已完成。
- **素材不足时**：输出已完成部分，并把缺口列成"待补充清单"交给用户，不要停下来等。
