# 客户需求分析与售前方案生成

把非结构化的客户材料，转成一份能直接进入方案撰写阶段的骨架：需求条目表、痛点结论、能力匹配矩阵、方案结构、交付与报价要点、风险与待澄清问题。

## 输入

任意组合，缺项不阻塞：

- 招标 / RFP / RFQ 文件（PDF、Word）
- 客户需求说明书、技术规格书
- 需求调研会议纪要、访谈记录
- 客户邮件、IM 聊天记录
- 现有架构文档、系统清单、数据量指标

## 工作流

### 第 1 步 材料清点与结构化

逐份材料读取，把叙述性文字拆成**需求条目**。每条包含：

| 字段 | 说明 |
| --- | --- |
| 编号 | R-001 递增 |
| 需求原文 | 客户原话摘录，不改写 |
| 出处 | 文件名 + 页码 / 段落，便于回溯 |
| 类型 | 业务 / 功能 / 非功能 / 技术约束 / 商务约束 |
| 明确度 | 明确 / 隐含 / 待澄清 |
| 交付相关 | 是否触发交付物或验收条件 |

### 第 2 步 需求分类

- **业务需求**：客户要达成的业务目标与指标（收入、成本、效率、合规）
- **功能需求**：系统要"能做什么"
- **非功能需求**：性能、可用性、安全、合规、SLA、可观测性、容灾等级
- **技术约束**：技术栈限定、网络与地域、数据驻留、既有系统对接
- **商务约束**：预算区间、工期与里程碑、付款方式、验收标准、罚则

### 第 3 步 痛点提炼

对每条业务需求，按 **现状 → 影响 → 期望** 三段式提炼，并保留客户原话作为佐证：

```
痛点 1：夜间批量作业窗口不足
  现状：日增数据 2.4 TB，现有窗口 4 小时
  影响：3 个下游报表次日 9 点前无法产出，业务例会延期
  期望：窗口压缩到 90 分钟以内
  佐证：「每天早会都在等数」——客户数据平台负责人，07-15 访谈
```

### 第 4 步 能力匹配矩阵

| 需求编号 | 客户期望 | 我方能力 / 产品 | 满足度 | 说明 |
| --- | --- | --- | --- | --- |
| R-007 | 双活容灾，RTO ≤ 15 min | 双 AZ + 跨区备份 | 完全满足 | 需客户确认第二可用区配额 |
| R-012 | 存量 51 TB 在线迁移不停机 | DTS + 双跑 | 部分满足 | 大表需分批，需窗口协调 |
| R-018 | 本地化报表引擎 | 无自有产品 | 需第三方 | 建议生态合作或替换方案 |

满足度取值：`完全满足` / `部分满足` / `需定制开发` / `需第三方` / `不满足（需引导客户调整需求）`。

### 第 5 步 方案结构

默认 14 章骨架，按项目类型裁剪：

1. 方案概述与理解客户业务
2. 现状分析与核心痛点
3. 总体架构设计
4. 分模块详细设计
5. 数据迁移 / 系统切换方案
6. 性能与容量设计
7. 安全与合规设计
8. 高可用与容灾
9. 可观测性与运维体系
10. 实施路径与分期计划
11. 项目组织与职责分工
12. 交付物与验收标准
13. 风险与应对
14. 商务说明与报价

### 第 6 步 交付与报价要点

- **工作分解**：按阶段（调研 / 设计 / 实施 / 迁移 / 测试 / 上线 / 保障）拆到可估算颗粒度
- **人天估算**：给出基准值与浮动区间，标明依赖前提（见下）
- **报价口径**（可覆盖，默认参考）：

| 项 | 默认值 | 说明 |
| --- | --- | --- |
| 人天单价 | $350 / 人天 | 如客户指定币种或预算口径，按客户调整 |
| 汇率与税 | 按签约主体确定 | 中东项目注意 VAT |
| 折扣策略 | 按总量阶梯 | 明确折扣不影响交付范围 |

- **假设与前置条件**：客户需提供的资源、环境、窗口、审批，逐条列明。这是报价免责的核心。
- **付款与验收**：里程碑分期、验收标准、验收争议处理。

### 第 7 步 风险与待澄清

- **风险登记册**：风险描述 / 概率 / 影响 / 应对措施 / 责任人
- **待澄清问题清单**：每条注明"为什么必须澄清"（不澄清会导致方案或报价偏差的方向）

## 输出交付物

| 交付物 | 格式 | 说明 |
| --- | --- | --- |
| 需求条目表 | Markdown / Excel | 全量需求 + 出处 |
| 痛点分析 | Markdown | 现状 → 影响 → 期望 + 原话 |
| 能力匹配矩阵 | Markdown / Excel | 满足度一眼可见 |
| 方案书骨架 | Markdown / docx | 到二级标题 + 每节要点 |
| 需求响应表 | Markdown | 逐条应答，用于投标 |
| 人天估算表 | Excel | 阶段 × 角色 × 人天 |
| 风险登记册 | Excel | 含应对与责任人 |
| 待澄清问题清单 | Markdown | 含影响方向 |

## 写作规范

1. **中英双语**。面向海外客户时，正文中英对照，术语保留英文原文（如 Landing Zone、RTO、SLA）。
2. **不夸大**。不用"业界领先""完美解决"这类无法验证的表述；改为可衡量的承诺。
3. **每条承诺都可交付**。方案里出现的功能、指标、时间，必须能映射到第 6 步的工作分解。
4. **数字可追溯**。所有容量、性能、人天数字标注来源或测算依据。
5. **区分事实与判断**。客户原话、既有系统指标属事实；容量测算、风险概率属判断，需标注为估算。

## 常见问题

| 问题 | 后果 | 规避 |
| --- | --- | --- |
| 把功能清单当方案 | 客户看不出价值，落入比价 | 每个功能都挂到痛点上 |
| 承诺无法交付的指标 | 验收阶段扯皮 | 非功能需求逐条标注"可达 / 需条件" |
| 漏掉客户已明确写的约束 | 直接废标 | 第 2 步"明确度"字段必须逐条过 |
| 人天不给浮动区间 | 变更时无谈判空间 | 基准 + 区间 + 依赖前提 |
| 假设条件没写进方案正文 | 客户事后不认 | 假设单独成章，正文引用 |

## 边界

- **不做**：代替客户决策、承诺具体法律条款、在缺少关键信息时硬出精确报价。
- **缺关键输入时**：先输出"基于现有材料的初步版"，并在待澄清清单里列出偏差方向，不要停下来等。
