# 数据热点库处理

把"哪些表/行/库在被频繁访问、为什么这些"说清楚，并给出可落地的优化方案（冷热分层、分库分表、查询改写、缓存、限流）。

## 输入

-  库表清单（含表大小、字段、分区键、索引）
-  访问日志（SQL 审计 / 慢查询日志 / 应用侧埋点）
-  业务高峰期的 QPS、RT、错误率数据

## 工作流

### 第 1 步 热点识别

按四个维度量化：

| 维度 | 指标 | 来源 |
| --- | --- | --- |
| 表级热点 | 读写 QPS TOP 10、扫描行数 TOP 10 | SQL 审计 / 慢查询日志 |
| 行级热点 | 同一主键访问频次 TOP 10 | 应用埋点 / Binlog 分析 |
| 时间热点 | 某时间段集中访问（如大促） | 时序聚合 |
| 资源热点 | 节点 CPU / IO / 锁等待 | 数据库监控 |

输出热点清单（含热度分、影响范围）。

### 第 2 步 根因分析

每条热点分三类根因：

| 根因类别 | 特征 |
| --- | --- |
| **业务模式** | 秒杀、大促、抢购、单点查询 |
| **数据模型** | 缺少分区、缺少二级索引、大字段 |
| **架构问题** | 全表扫描、跨库 join、长事务 |

### 第 3 步 优化方案选型

| 场景 | 推荐方案 | 工作量 |
| --- | --- | --- |
| 单点查询（按 user_id） | PolarDB / Hologres 行存表 + 索引 | 中 |
| 大表全表扫描 | 分区表 + 列存（Hologres） | 中 |
| 写热点（秒杀库存） | Tair / Redis 原子计数 + 异步落库 | 中 |
| 读热点（详情页） | CDN + 阿里云 ElasticCache | 低 |
| 历史数据访问 | 冷热分层：热数据 PolarDB、冷数据 OSS/MaxCompute | 中-高 |
| 倾斜任务（MapReduce） | Salting 字段 + 自定义 partitioner | 中 |
| 跨库 join 热点 | 数据冗余到宽表 + 物化视图 | 高 |

### 第 4 步 输出实施计划

```
- 短期（< 1 周）：加索引、加缓存、改 SQL
- 中期（2-4 周）：分库分表、冷热分层
- 长期（> 1 月）：数据模型重构、读写分离链路升级
```

每条方案给出：

-  预期收益（QPS 提升倍数、RT 下降百分比）
-  实施成本（人天 + 资源成本）
-  风险与回滚预案

### 第 5 步 验证与监控

```
- 上线后 24h 重点观察：热点表 RT、错误率、连接数
- 对比优化前后的同指标
- 设置告警阈值（RT > 阈值、错误率 > 阈值）
```

| 文件 | 格式 |
| --- | --- |
| 热点识别清单 | Excel |
| 根因分析 | Markdown |
| 优化方案 | Markdown（含优先级） |
| 实施计划 | Markdown（按短/中/长期） |
| 监控告警方案 | Markdown |

## 边界

- **不做**：数据库内核层面的热点重写（需云厂商定制）。
- **依赖**：访问日志的时间窗口与采样率由客户提供，采样不足会导致热点识别偏差。
