# 大数据迁移评估 — 我方口径三层模型

给大数据迁移/改造项目算**人力工作量**。核心纪律：**用我方评估逻辑，不沿用客户或友商给的人月数字**。

客户/友商表里的人月只能当**交叉校验参照**，不能当输入。看到对方的"113.5 人月""342.8 人天"这类数字，要做的是**用我方模型独立算一遍再对比差异**，而不是在它上面乘系数。

---

## 最高优先级纪律（P0）

| # | 纪律 | 具体含义 |
|---|------|---------|
| 1 | **独立重算** | 客户/友商的人月数不得作为基数被缩放。只能作为"差异对比"一栏出现 |
| 2 | **三层不重复计** | 同一份工作只能落在模型1/2/3 其中一层。判重规则见下文"分层判定" |
| 3 | **超目录必须显式标红** | 标准服务目录里没有的计费项、或超出目录计费上限的量，必须单独成表并标注"需单独商务谈判"，不得静默按目录单价折算 |
| 4 | **系数连乘、来源可追溯** | 每个修正系数都要写明触发依据（哪条事实触发的），不得凭感觉给 |
| 5 | **给区间不给点值** | 输出必须是 低/中/高 三值，中值=(低+高)/2。单点数字禁止直接对外 |
| 6 | **不猜单价** | 人天单价必须用户显式给或从 references/baseline-params.md 的既有价目取，且标明取的是成本价还是刊例价 |

---

## 三层模型

```
大数据总人力 = 模型1（复杂度分级）+ 模型2（标准服务目录）+ 模型3（超服务目录项）
```

### 模型1 — 复杂度分级（应用/模块级改造）

对每个**需要代码级改造或异构适配**的大数据应用/模块打 D1–D4 四维分（各 1–5），取平均 → 落等级 → 查基准人天区间 → 乘修正系数。

| 维度 | 含义（大数据场景） |
|------|------|
| D1 架构复杂度 | 源端托管服务→目标端对端的异构程度：同构搬迁 1 / 组件替换 3 / 数仓+计算引擎+编排整栈重构 5 |
| D2 数据复杂度 | 数据量级、表数、元数据规模、Schema 与 SQL 方言差异：单库小表 1 / 万表级元数据 + 方言重写 5 |
| D3 耦合度 | 被多少上下游依赖、是否为公共 SDK 或调度收口：独立应用 1 / 全平台依赖的 SDK、调度器 5 |
| D4 改造深度 | Rehost 1 / Replatform 3 / 代码级 Refactor（SQL、UDF、作业逻辑重写）5 |

等级与基准人天：

| 等级 | 平均分区间 | 基准人天 低 | 高 |
|---|---|---|---|
| L1-简单型 | [1.0, 1.8) | 5 | 7 |
| L2-普通型 | [1.8, 2.6) | 7 | 12 |
| L3-中等型 | [2.6, 3.4) | 15 | 25 |
| L4-复杂型 | [3.4, 4.2) | 30 | 50 |
| L5-极高难度 | [4.2, 5.0] | 60 | 90 |

修正系数**连乘**（PRODUCT），触发条件见 `references/baseline-params.md`：

| 系数 | 取值 | 触发条件 |
|---|---|---|
| 自动化 | ×0.8 | 有可用的全自动迁移工具覆盖该场景；异构改造一律不给 0.8 |
| 文档/源码 | ×1.5 | 客户未开放源码仓库或未提供现有架构文档 |
| 网络/带宽 | ×1.2 | 无专线、或带宽 <100Mbps、或搬迁数据 >500GB |
| 合规/安全 | ×1.3 | 等保/审计/数据不出域等额外要求 |
| 其他 | 手工 | 必须写明理由 |

> 带宽系数在模型1 与模型2 中只能计一次。默认计在**模型2**（数据搬迁才是带宽敏感的），模型1 取 1.0。

### 模型2 — 标准服务目录（资源搬迁）

有标准计费项的搬迁工作，按 `资源量 ÷ 标准产能 = 人天`。产能基准见 `references/baseline-params.md`。

**强制做两件事**：
1. **上限校验** — 目录对存储/数据库等项有计费量上限（如对象存储 0–102400GB）。超上限的量必须拎出来单列，标注超出倍数。
2. **替代算法** — 对超上限项，不能按 `量÷产能` 线性外推（20PB ÷ 2000GB/人天 = 9429 人天，荒谬）。改用"**工具操作人天 + 传输期值守人天**"：
   ```
   替代人天 = 工具部署配置调优人天 + 传输日历天数 × 值守系数(默认0.2)
   传输日历天数 = 数据量 ÷ (带宽有效吞吐 × 每日传输小时)
   ```
   同时必须给出带宽场景表（多档带宽 → 日历工期），因为**工期风险往往比人力风险大**。

### 模型3 — 超服务目录项（无计费项的工作）

目录里**查不到计费项**的工作，按"产能定律"逐项定价，全部标注"需单独商务谈判"。典型大数据场景（产能基准见 references）：

- 作业改造：Spark ETL / Streaming / Python Shell / EMR Spark SQL / UDF / Shell 任务
- 元数据迁移：Glue Catalog / Hive Metastore / 数仓表结构
- SQL 方言重写：Redshift SQL / Athena SQL / 存储过程
- 数据一致性校验：离线任务抽样校验、报表比对
- 实时链路：Kinesis/Kafka → Flink/Oceanus 的 UDF、SQL、Jar 作业
- 性能调优、迁移工具/脚本开发、环境搭建、双跑并行、割接

> **先查目录再定价**。执行时必须真的去读目录文件并 grep 关键词（大数据/数仓/数据湖/Hadoop/Spark/EMR/Hive/Kafka/ETL/ClickHouse/Doris/Flink/MaxCompute），把"命中 0 项"这个事实写进结论——它本身就是最重要的商务结论。

### 分层判定（避免重复计）

| 工作性质 | 归属 |
|---|---|
| 应用/模块需要改代码、换组件、适配方言 | 模型1 |
| 纯资源搬过去，目录有计费项 | 模型2 |
| 有明确数量、按条/表/个计的改造工作，目录无计费项 | 模型3 |
| 模型1 已按模块整体估的应用，其内部作业不再进模型3 | 只算模型1 |

实践上：模型1 覆盖**平台/模块级**，模型3 覆盖**作业/对象级**且这些作业不属于任何已在模型1 中整体计价的模块。二者边界必须在输出的"评估模型说明"页写清。

单价见 `references/baseline-params.md`。换算：**1 人月 = 22 人天**。

## 执行步骤

### 步骤 0 — 输入校验（强制）

必须拿到以下材料，缺哪项就如实列出并说明其对结果的影响，**不得用默认值静默填补**：

1. 源端资源清单（计算/存储/数据库/托管大数据服务，带数量与容量）
2. 大数据作业清单（按类型分类计数：ETL 条数、SQL 数、表数、UDF 数）
3. 我方标准服务目录文件
4. 应用/模块清单（用于模型1 打分）

缺 3 → 无法做超目录判定，输出降级为"仅人力估算，不含商务口径"。
缺 1、2 → 相关项按"待客户确认"留空，**不估数**。

### 步骤 0.5 — 查目录（强制）

读标准服务目录，grep 大数据关键词，记录命中项与命中数。这是模型2/3 分界的唯一依据。

### 步骤 1 — 模型1 打分

按 D1–D4 标尺逐模块打分，每个分数必须在备注里写明打分依据（引用的具体事实，如"Glue Catalog 9800 表 + Athena + Lambda"）。
打分标尺与常见异构迁移路径对照见 `references/scoring-rubric.md`。

### 步骤 2 — 模型2/3 测算

按产能基准逐项算，超上限项走替代算法并出带宽场景表。

### 步骤 3 — 确定性计算（强制用脚本）

```bash
python3 ~/.claude/skills/bigdata-migration-assessment/scripts/bd_assess.py \
  --config /path/to/input.json \
  --out /path/to/输出-大数据人力评估.xlsx
```

退出码非 0 → 输入不完整，脚本拒绝产出。**不得手工凑数**。
输出 xlsx 固定 6 页：`01-评估模型说明` / `02-模型1·复杂度分级` / `03-模型2·标准服务目录` / `04-模型3·超服务目录项` / `05-汇总·阶段·岗位·成本` / `06-待客户确认清单`。

### 步骤 3.5 — 回写既有评估表（可选）

若项目已有《应用复杂度评估 V7》体系的工作簿，把模型1 的单元回写进 `应用评估` 页，复用其原生公式链：

```bash
python3 ~/.claude/skills/bigdata-migration-assessment/scripts/inject_v7.py \
  --workbook "/path/to/应用复杂度评估 V7.xlsx" \
  --config /path/to/input.json \
  --out "/path/to/应用复杂度评估 V7-含大数据评估.xlsx" \
  --team "团队4-大数据"
```

脚本只填 A–G、M–Q、AC、AD 列，**不动原表公式**，并追加一页`大数据评估说明`。

### 步骤 4 — 差异对比（强制）

必须出一栏：我方结果 vs 客户/友商口径 vs 我方现有报价，并**定位差异根因**。
根因通常是下列之一，逐条排查：

- 技术栈口径错配（按同构集群搬迁估了异构托管服务改造）
- 范围漏项（某个承载主要体量的平台不在已报价范围内）
- 体量未穿透（只看了集群数没看数据量/作业数）
- 责任矩阵错位（以为是客户做的工作实际落在我方）

### 步骤 5 — 待客户确认清单

按 P0/P1/P2 分级输出，每项写明"缺了它会导致什么偏差"。模板见 `references/customer-info-checklist.md`。
同时给出**可操作的降本杠杆**，例如"客户开放源码+架构文档 → 文档系数 1.5→1.0 → 节省 N 人天 ≈ M 人月 ≈ ¥X"。
