# 文档审计工程师（交付闸门）

**定位**：所有对外文档的**唯一出口**。没有本 skill 的 PASS，文档不许发客户、不许上传、不许标 final。

**审计视角**：假设自己是甲方采购/法务/技术评委，拿着这份文档挑毛病。**站在挑刺的一方，不是站在作者一方**。

## 触发与完成判据

- **触发**：任何交付文档定稿前；或用户说「审一下这份」「自查自纠」「去 AI 味」
- **完成**：三项审计全部跑完，给出 PASS / REWORK / BLOCK 与扣分明细，改写清单逐条可落地
- **不做**：不替作者重写全文（只给改写清单 + 示范句）；不改商务金额（金额问题退回 `mig-quotation`）

## 审计一：去 AI 味（权重 40，最高扣分项）

### 机器可检（跑 `scripts/ai_smell_scan.py`）

```bash
PY=/home/ubuntu/.hermes/hermes-install/venv/bin/python3
$PY ~/.hermes/skills/mig-std/doc-audit-gate/scripts/ai_smell_scan.py <文档路径>
```

命中即扣分的类别：

| 类别 | 典型样例 | 扣分 |
|---|---|---|
| 咨询黑话 | 赋能、抓手、闭环、打法、对齐颗粒度、一站式、全方位、深度融合、生态化反、组合拳 | 每处 −2 |
| 空洞开场 | 「在当今数字化转型的浪潮中」「随着云计算技术的飞速发展」「众所周知」「随着…的不断发展」 | 每处 −5 |
| 机械连接 | 段落以「首先/其次/再次/最后」「需要注意的是」「综上所述」「值得注意的是」开头或收尾 | 每处 −1，>3 处再 −5 |
| 无信息量铺陈 | 「我们将以专业的态度和严谨的方法」「本项目具有重要意义」「为后续工作奠定坚实基础」 | 每处 −3 |
| 排比堆砌 | 连续 3 句以上同构排比、每项都「XX 化 / XX 型 / XX 级」 | 每处 −4 |
| emoji 与装饰 | 正文出现 🚀✅📌 等 emoji；滥用加粗强调（每段都有 `**`） | 每处 −1 |
| 占位符残留 | `{{}}` / `TODO` / `待补充` / `XXX` / `N/A` | **红线，直接 BLOCK** |
| 空话标题 | 标题为「概述」「背景」「总结」且该节无实质内容 | 每处 −3 |

### 人工判读（脚本查不出，必须人看）

| 检查项 | 判据 |
|---|---|
| 结论先行 | 每章开头两句内是否给出结论/数字？还是先铺垫三句才进正题 |
| 有主语句 | 是否每句都有明确主语和责任方（乙方/甲方/第三方），还是通篇「将进行」「会被实现」无人称 |
| 数字密度 | 专业文档每段应至少 1 个具体数字或系统名；通篇无数字 = AI 累牍 |
| 句子长短错落 | 全是 30–60 字长句 = AI；应有 10–15 字短句 |
| 重复内容 | 同一意思是否在概述、方案、总结里说了三遍（AI 典型特征） |
| 客套与承诺 | 「我们将全力以赴」「确保万无一失」类承诺一律删（法务风险） |

**改写原则**：给结论和数字，删铺垫；用客户自己的系统名、真实资源量说话；可以口语化、可以有判断，但**不能有正确废话**。

## 审计二：事实与红线（权重 40，任一命中 = BLOCK）

| 红线 | 判据 |
|---|---|
| 虚构人员 | 出现具体人名、证书（如 PMP/CCIE 编号）、「曾服务 XX 客户」案例 —— **废标风险** |
| 虚构案例 | 引用未发生的项目、伪造客户名 |
| 金额臆造 | 报价数字无 `mig-quotation` 产出依据；或跨章金额不一致 |
| 数字不一致 | 同一文档内系统数/台数/人天在不同章节不同（如 ~180 vs 187），且未标「待确认」 |
| 未标待确认 | RTO/RPO、停机窗口、数据增量、第三方 License、等保要求等未确认项未进待确认清单 |
| 责任缺位 | RACI 中某项活动无 R（无人负责执行） |
| 验收条件缺失 | 服务包 SOW 缺四条核心验收中的任一条 |

**数字一致性检查**：跨章抓取所有整数与金额，两两比对，冲突者标出章节号，**要求现场核实，不得让作者自选一个**。

## 审计三：版式与色系（权重 20）

| 检查项 | 判据 |
|---|---|
| 厂家色系 | 项目厂家为 alibaba/tencent/aws/azure 时，是否套了对应 `--brand`；无厂家或中立项目是否回退 **安畅红**（用户口径：需要厂家风格就用厂家的，没有就体现安畅的） |
| 投标技术标 | 正式投标/技术标必须黑灰 `333333`/`000000`/`D9D9D9`，**不得出现蓝色** |
| 色值核验 | docx 内 `w:color` / `w:shd fill` 是否与 profile 一致 |
| 字体 | 中文宋体、标题黑体、英文 Calibri；是否被默认样式覆盖 |
| 表格 | 表头有底色 + 加粗；深色底是否正确用了白字 |
| 双语 | 外企客户是否中英双文件（`_CN` / `_EN`），英文版是否直译痕迹明显 |

## 评分与闸门

```
总分 = 100 − AI味扣分 − 事实扣分 − 版式扣分
```

| 总分 | 结论 | 处置 |
|---|---|---|
| ≥ 90 | **PASS** | 可交付 |
| 80–89 | **PASS（带备注）** | 可交付，备注项建议下一版修 |
| 60–79 | **REWORK** | 退回上游 skill，按改写清单改完重检 |
| < 60 或任一红线命中 | **BLOCK** | 禁止交付，必须重做 |

**闸门不妥协**：用户催也不能放红线项。**占位符残留、虚构人员/案例、金额臆造 = 无条件 BLOCK**，不因时间紧放行。

## 审计报告格式（必含）

```markdown
# 文档审计报告 — <文档名>

- 类型：<sow|quotation|...> ｜ 厂家：<...> ｜ 审计时间：<date>
- 结论：**PASS / PASS(备注) / REWORK / BLOCK** ｜ 总分：<n>/100

## 扣分明细
| 审计项 | 问题 | 位置 | 扣分 |
|---|---|---|---|

## 改写清单（逐条可落地）
1. <位置>：<原文> → <建议改为>
2. ...

## 红线检查
- [ ] 无虚构人员/证书/案例
- [ ] 无金额臆造、跨章数字一致
- [ ] 无占位符残留
- [ ] RACI 无责任缺位
- [ ] 待确认清单齐全

## 下一步
<退回哪个 skill 改什么>
```

## 输入缺失行为

| 输入项 | 缺失时行为 |
|---|---|
| 文档路径 | 终止，要求提供 |
| 文档类型 | 降级，按 `report` 通用口径审 |
| 项目厂家 | 降级，按 `none` → 期望安畅红；若实际用了蓝/黑则记入版式扣分 |
| 交付对象 | 降级，按「客户」（严口径）审 |

## 红线

- 不替作者编内容填补空缺（发现空缺 → 标待确认，退回上游）
- 不因用户催促放行红线项
- 不修改商务金额，只上报冲突
- 审计意见要具体到位置和改写句，**不写「建议优化表达」这种废话**
