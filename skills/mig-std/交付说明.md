## 一、这是什么

项目启动阶段（立项 → 评估 → 报价 → SOW）的标准化 skill 集。把原来散在聊天里的口径固化成可复用资产，解决三个问题：

1. **路由重叠**：多个 skill 抢同一句话，靠 description 边界写死
2. **输入缺失时瞎猜**：每个缺失场景预定义「取数 / 降级 / 升级」三条路，无头模式不卡死
3. **产出不可编排**：固定 JSON schema，让编排 skill 能直接读 conclusion 调 chain

## 三、怎么用

### 主路径

```
用户给材料 + 说期望产出
  → mig-startup-orch 判定路由
  → 调对应叶子
  → 叶子回 JSON（conclusion / confidence / suggested_actions / escalation）
  → orch 读 conclusion，决定继续 chain 还是升级给人
```

### 单独触发某个叶子也行

| 你说 | 走 |
| --- | --- |
| 新项目立项、要填项目信息表 | mig-project-intake |
| 有清单/只读授权、要评估规模 | mig-resource-assessment |
| 有评估报告、要报价 | mig-quotation |
| 有项目信息+评估、要 SOW | mig-sow-generator |

### 关键口径

- **AC-MIG $350/人天**（取自 workbuddy-rules/references/selling.md）
- **SOW 标准 14 章**（templates/SOW模板.md，含附录 A 待确认清单、附录 B 术语）
- **RTO/RPO 未确认 → 只能出预报价，SOW 不得标 final**
- **待确认清单五项**：账号权限、网络互联、数据一致性、割接窗口、回滚条件

## 六、已知边界

- `mig-resource-assessment` 声明依赖 `mig-cloud-adapter`。拿不到只读凭据会降级并升级，不会硬跑。可手动喂采集结果让它跑通。
- `aggregate.py` 只出 `coverage` / `missing_ids` / `gaps` / `by_domain` 四项计数。规格映射、容量合计由 skill 正文基于 `collected` 明细自行完成，**不得声称由脚本产出**。
- 报价相关脚本不联网、不写外部系统，纯本地计算。
