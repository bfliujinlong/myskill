# PCS RFP Analyze — RFP 采购要求提取

唯一目标：把**正式 RFP / 采购需求书**拆解为可追溯的采购要求（Requirement）与约束（Constraint）清单，并在清单之上产出招标分析报告（资质匹配 / 覆盖度 / 评分解读 / 竞争态势 / 投标决策建议），供后续应答覆盖与投标决策使用。

> 两段分层，纪律不同：**要求清单（步骤 1）只提取采购方要求，不评估、不补造安畅能力**；**招标分析（步骤 1.5）才做我方视角的匹配与决策**，且分析结论与要求清单物理分离，不得回写污染要求清单。本 Skill 不撰写应答稿内容。

---

## 支持范围

**支持：**
- 读取正式 RFP 原文（用户粘贴文本，或 `01_客户输入/01_RFP与采购文件/` 下已存放的文本）；
- 逐条抽取要求（强制/可选）、约束、评分维度、截止时间、资质要求；
- 为每条要求分配编号并回指原文来源；
- 在清单之上产出招标分析报告（资质匹配 / 覆盖度 / 评分解读 / 竞争态势 / 投标决策 PROCEED-HOLD-DECLINE）。

**暂不支持（v0.1 边界）：**
- 编写应答稿、方案或报价；
- 从会议记录/口头意向"推断"出 RFP；
- **无正式 RFP 的 pre-RFP 机会走留判断**（超出本插件范围；pre-RFP 沟通请用 `ms-customer-communication` 归档）。

> 注：资质/覆盖度的"满足与否"判断仅在**步骤 1.5 招标分析**中进行，且须标数据源；步骤 1 要求清单仍严守"只提取不评估"。

## 执行步骤

### 步骤 0 — 前置检查（强制）

使用 Read 读取当前 Project 根目录 `project.yaml`：存在→继续；否则 `BLOCKED: 当前目录不是已初始化的 PCS Project，未找到 project.yaml`。

### 步骤 0.5 — 正式 RFP 存在性闸门（强制）

必须确认存在**正式 RFP / 采购需求书**。判定为"存在"须满足：用户明确提供 RFP 正文文件或粘贴 RFP 原文，且内容具备正式采购要求特征（如需求条目、评分、截止时间、正式发布方）。

若不存在正式 RFP（仅有会议记录、口头意向、探索性交流），**停止并输出**：

```
BLOCKED: 未提供正式 RFP / 采购需求书，本 Skill 不在无正式 RFP 时运行；请先获取正式采购文件；pre-RFP 探索期沟通请用 ms-customer-communication 归档。
```

**禁止**：不得从会议纪要、沟通记录或模型常识"补造"或"推断"出一份 RFP。

### 步骤 1 — 提取要求与约束（PREVIEW 模式）

按 `references/output-template.md` 生成，包含：项目概况、强制要求清单（编号+原文引用）、可选要求、约束与资格、评分维度、关键时间节点、提取缺口。

**提取纪律（强制）：**
- 只提取 RFP 原文中明确出现的内容，每条要求标注来源（章节/条款号）；
- **不补造安畅公司能力**，不写"安畅可满足/不满足"之类应答判断；
- 原文含糊处标记"原文未明确/待澄清"，不替客户补全；
- 不改变要求的强制性等级（强制 vs 可选）。

**数量原文保真纪律（强制）：**
- RFP 提及对象（如 K8s 集群、中间件、云主机）但**未提供具体数量**时，只能写：
  > RFP 提及<对象>，但未给出具体数量，待确认。
- **禁止写**：原文若干、约若干、通常为若干、若干套、或者任何看似来自客户的数量描述。
- 只有 RFP 原文**真的包含"若干"一词**时，才允许引用该词，且必须加原文引注。
- 输出必须包含 `quantity_status` 字段：`explicit`（原文有明确数量）/ `unknown`（原文未给出数量）/ `approximate`（原文使用约/大约/左右等近似表述，按原文保留）。

**资质类型保真纪律（强制）：**
- RFP 要求资质但**未明确具体资质类型**时，只能写：
  > 具体资质类型和要求待澄清。
- CAICT、等保、云厂商认证等行业示例**可以出现**，但必须进入独立区：
  > **AI 建议 / 候选澄清方向（非 RFP 明确要求）**
- **不得**把 AI 举例写入：RFP 强制要求、原文来源、客户已确认资质要求。

**默认输出为 PREVIEW**：在对话中展示，不写入文件。

### 步骤 1.5 — 招标分析（分析维度，吸收原 opportunity-intake 投标决策）

在要求清单（步骤 1 的 R1-Rn）**之上**、作为**独立报告章节**输出 5 个分析维度。数据源须为显式输入或注入的 KB 语义键，缺失一律标"待补充/待确认"，不虚构、不补造。

| # | 维度 | 产出 | 数据源 | 纪律 |
|---|---|---|---|---|
| 1 | 资质匹配 | RFP 资质要求逐条 vs 我方资质清单（满足 / 缺口 / 待核） | KB `company_intro`（未注入→WARN 待补充） | 缺口据实列，不为过关粉饰 |
| 2 | 目录/功能覆盖度 | 强制要求 vs Service Catalog（完全 / 部分 / 不覆盖 + 覆盖率%） | KB `service_catalog_master`（母版反查，非全量入） | 不覆盖项据实标，不夸大覆盖 |
| 3 | 商务评分解读 | 评分权重 → 强弱项 → 响应侧重建议 | RFP 评分表原文 | 权重来自原文；无评分表写"原文未提供评分权重" |
| 4 | 竞争态势 | 对手预判 + 我方相对位置 | 显式输入 / 已知事实 | 无输入写"待销售补充情报"，不臆测具体对手 |
| 5 | 投标决策建议 | **PROCEED / HOLD / DECLINE** + 理由 + 决策依赖项 | 前 4 维综合 | 见下决策纪律 |

**投标决策纪律（强制，吸收原 opportunity-intake go/no-go）：**
- 结论只能三选一：`PROCEED`（建议投标）/ `HOLD`（暂缓，待关键条件明确）/ `DECLINE`（建议放弃）；
- 每个结论必须给出**决策依据**（引用前 4 维具体缺口/优势）与**决策依赖项**（哪些待确认项一旦明确会翻转结论）；
- **资质硬缺口**（RFP 强制资质我方明确不具备且不可分包补足）→ 不得给 PROCEED，至少 HOLD 并显式标注该硬门槛；
- 决策是**建议**，非承诺：措辞为"建议/倾向"，最终由商务/管理层裁定；
- 无正式 RFP 时本步骤不运行（步骤 0.5 已闸门拦截）；**完全无 RFP 的机会走留判断不在本插件范围内**，pre-RFP 探索期沟通请用 `ms-customer-communication` 归档。

**分析与提取物理分离（强制）：**
- 招标分析结论**不得回写**步骤 1 的要求清单（要求清单保持采购方原文视角）；
- 分析中我方能力/资质引用须标数据源与版本，未注入 KB 的结论标"待补充"，不用模型常识补造资质或覆盖度。

**默认输出为 PREVIEW**：要求清单 + 招标分析报告一并在对话中展示，不写入文件。

### 步骤 2 — 保存（仅用户明确要求时）

须同时满足，缺一即 `BLOCKED` 不写入：

| 条件 | 失败输出 |
|---|---|
| 客户名称已明确 | `BLOCKED: 客户名称待确认，无法生成文件名` |
| 正式 RFP 已确认存在 | `BLOCKED: 未提供正式 RFP，无法分析` |
| 目标目录 `03_方案与应答/02_RFP应答与总控/` 已存在 | `BLOCKED: 目标目录不存在，请先运行 ms-project-init` |
| 目标文件不存在 | `BLOCKED: 文件已存在，路径 <路径>，不覆盖` |

目标文件名：`YYYY-MM-DD-客户名称-RFP要求清单.md`

**写入边界**：只在既有标准目录创建缺失目标文件；不改写客户原始 RFP；不写入 Company KB。
