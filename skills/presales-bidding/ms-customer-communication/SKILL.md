# PCS Customer Communication — 客户沟通记录

v0.1 唯一目标：将用户粘贴的一段客户沟通文字，整理成一份结构化的客户沟通记录。

---

## v0.1 支持范围

**支持：**
- 用户直接粘贴文本；
- 用户显式提供客户名称和沟通日期，或从文本中提取；
- 缺失信息统一标记"待确认"。

**暂不支持（v0.1 边界）：**
- 外部会议系统、妙记或会议纪要自动拉取；
- CRM、Base 或其他外部系统集成；
- Q&A 独立文档、需求记录、交流总结等多文档分类；
- 自动同步任务、风险或机会信息至项目目录；
- 批量处理。

## 执行步骤

### 步骤 0 — 前置检查（强制）

使用 Read 工具尝试读取当前 Project 根目录下的 `project.yaml`：

- `project.yaml` 存在且可读 → 继续；
- `project.yaml` 不存在或不可读 → 停止，输出：

```
BLOCKED: 当前目录不是已初始化的 PCS Project，未找到 project.yaml
```

**禁止**：不创建或修改 `project.yaml`；不引用其他工作区配置文件；不使用 Bash 命令完成本检查（allowed-tools 中无 Bash）。

### 步骤 1 — 接收输入

从用户输入中识别：

| 字段 | 来源 | 缺失处理 |
|------|------|----------|
| 客户名称 | 用户显式提供 或 文本提取 | 标记"待确认" |
| 沟通日期 | 用户显式提供 或 文本提取 | 标记"待确认" |
| 沟通文本 | 用户粘贴 | 必需，缺失则停止 |

**禁止**：用 Workspace 名称、环境变量或模型推断替代用户输入作为客户名称。

### 步骤 2 — 生成沟通记录（PREVIEW 模式）

按 `references/output-template.md` 的 8 个部分生成文档。

**生成规则：**
- 只记录输入中明确出现的内容；
- 不把模型推断写成已确认事实；
- Blocker 和行动项必须标记"候选，待确认"；
- 无明确决策时，决策栏写"本次无明确决策"；
- 未知信息统一写"待确认"，不虚构。

**默认输出为 PREVIEW**：在对话中展示，不写入任何文件。

### Source Fidelity Gate（来源保真，强制）

处理沟通记录时必须遵守：

1. 用户明确提供的客户名称、日期、阶段、Owner 等字段必须原样保留，不得改写为"待确认"；
2. 客户直接提出的问题优先原意保留，不得用模型生成的问题替换；
3. 输入中明确的下一步行动必须原样进入候选行动项，不得替换或新增；
4. 模型建议不能替换原始行动；
5. 如确有必要给建议，必须放在单独的"可选建议"区，并明确标记：`模型建议，非客户原话，待用户确认`；
6. v0.1 默认不输出"可选建议"区，除非用户明确要求；
7. 必须严格区分以下四类，不得混用或升级：
   - **已确认事实**：输入中明确陈述的客观情况；
   - **客户明确问题**：原文中客户直接提出的问题，原意保留；
   - **探索性表达**：含"希望了解""是否可以""初步考虑""可能需要"等表述，不得升级为已确认需求；
   - **模型推断**：模型根据上下文推断的内容，不得写入前三类；
8. "希望了解""是否可以""初步考虑""可能需要"等表述一律不得升级为已确认需求；
9. 不得补造人员角色、责任方、截止日期、预算、SLA 指标或交付物；
10. 对输入进行结构化可以改写语序，但不得改变事实、问题、行动和确定性等级。

### 四层信息分层（Four-Layer Classification，强制）

将客户信息分为四层，逐条归位，不得笼统输出"本次沟通尚未形成明确需求"：

1. **已确认业务需求 / 目标**：客户明确陈述的采购决定、业务目标。
   - "公司已经决定采购/引入外部托管运维" → 已确认业务需求；
   - "替换纯人力值守模式" → 已确认业务目标。
2. **已确认项目边界**：客户明确圈定的范围取舍。
   - "本次聚焦基础托管、安全托管暂不纳入" → 已确认项目边界。
3. **目标服务范围（待进一步确认）**：客户表达的期望覆盖面，但尚未形成正式约束。
   - "希望覆盖 7×24 监控、告警响应、常规变更" → 目标服务范围，尚需进一步确认（不写成已确认需求，也不降级为纯问题）。
4. **待澄清问题**：疑问、咨询、"客户关心"的事项。
   - 统一纳管、权限、K8s、计费、案例等 → 待澄清问题。

**分层纪律：**
- 明确采购决定和业务目标必须进入第 1 层，不得降级为"尚未形成需求"；
- 明确范围取舍进入第 2 层；
- 期望覆盖面进入第 3 层并标注"待进一步确认"，不得升级为已确认需求，也不得笼统丢入待澄清；
- 疑问/咨询进入第 4 层；
- 同一内容不得跨层重复；
- 仅当四层全空（既无采购决定、无目标、无边界、无期望范围、无问题）时，才可写"本次沟通尚未形成明确需求"。

允许进入第 1/2 层的确认表达示例：客户明确要求……、必须……、已经决定……、确定包含……、客户确认采用……、正式 RFP 规定……。

### 步骤 3 — 保存（仅用户明确要求时）

用户明确要求保存后，必须同时满足以下全部条件，缺一即输出 `BLOCKED`，不写入：

| 条件 | 检查方式 | 失败输出 |
|------|----------|----------|
| 客户名称已明确（非"待确认"） | 来自步骤 1 | `BLOCKED: 客户名称待确认，无法生成文件名` |
| 沟通日期已明确（非"待确认"） | 来自步骤 1 | `BLOCKED: 沟通日期待确认，无法生成文件名` |
| `project.yaml` 存在 | Read 工具读取 | `BLOCKED: 未找到 project.yaml` |
| 目标目录 `01_客户输入/03_会议访谈与沟通/` 已存在 | Read 工具探测 | `BLOCKED: 目标目录不存在，请先运行 ms-project-init` |
| 目标文件不存在 | Read 工具探测 | `BLOCKED: 文件已存在，路径 <路径>，不覆盖` |

目标文件名格式：`YYYY-MM-DD-客户名称-客户沟通记录.md`

**写入边界**：只在既有标准目录中创建缺失的目标文件，不修改项目骨架，不自动创建任何目录。

**禁止自动写入以下目录：**
- `00_项目管理/02_计划与协同/`
- `00_项目管理/03_决策风险与问题/`
- `02_机会与策略/`
- Company KB（任何路径）

Blocker、行动项和机会信息须经用户明确确认后再升级。

## 输出状态声明

每次执行必须在结尾明确声明以下三种状态之一：

- `PREVIEW` — 仅对话预览，未写入任何文件；
- `CREATED: <路径>` — 文件已创建；
- `BLOCKED: <原因>` — 因冲突或信息不足停止，未写入。
